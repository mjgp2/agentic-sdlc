About

Why this guide exists.

I think AI coding is most useful when it strengthens normal engineering discipline instead of bypassing it. This site is a practical guide to keeping specs, architecture, tests, worktrees, review evidence, and release gates visible while using coding agents.

Point of view

The agent should work inside the SDLC, not outside it.

Teams already know how to move a story from scope to requirements, design, build, test, review, UAT, and release. AI coding changes the mechanics of that flow, but it should not remove the need for clear tickets, durable repo text, explicit architecture guidance, automated checks, human review, and production safety controls.

I often think about coding agents like a very fast junior development team. They can produce useful work quickly, but the first pass may be incomplete, mis-scoped, or slightly off the local architecture. That is not a reason to avoid them; it is a reason to give them better specs, smaller lanes, review loops, CI gates, and production guardrails.

The goal of this guide is to show how I structure that work for TypeScript projects: keep context in Markdown, use Mermaid diagrams where they clarify behavior, give agents repo-local instructions, isolate implementation in worktrees, and make every PR carry the evidence a reviewer needs.

The material comes from practical delivery patterns I use around TypeScript services, pnpm workspaces, local agent guidance, PR review loops, CI gates, and production-safety controls. It is intentionally opinionated because generic AI coding advice tends to ignore the repo and release mechanics that make teams trust the work.
