Lifecycle guide

Follow the SDLC, then add AI-specific operating detail.

A user story moves through requirements, design, build, test, and acceptance. Each step produces repo text the agent can use and evidence reviewers can inspect.

Requirements

The ticket is the contract.

Use Jira, Linear, or a repo-local issue template to capture outcome, scope, non-goals, acceptance criteria, feasibility, reviewer roles, risk, and verification commands. Use the agent to challenge gaps before implementation instead of discovering ambiguity in the diff.

Design

Put architecture where the agent will read it.

  • Keep ADRs, contracts, boundary rules, and Mermaid diagrams in the repo.
  • Ask AI to review sequence diagrams for missing branches, retries, and ownership confusion.
  • Add data-flow diagrams and threat models when the change touches trust boundaries.
  • Use database diagrams or ERDs when persistence, migrations, or ownership of tables changes.
  • Require specialist DB migration review for schema changes, backfills, data movement, or destructive operations.
  • Use AGENTS.md to turn architecture choices into edit-time rules.
  • Require a design gate when the story changes persistence, APIs, auth, or package boundaries.

Text artifacts

Prefer durable text over transient chat context.

  • Markdown spec: problem, constraints, acceptance, non-goals.
  • Mermaid diagram: workflow, sequence, state, dependency, data flow, threat model, or database shape.
  • Scenario file: actors, setup, actions, assertions, negative paths.
  • Architecture note: decision, rejected alternatives, proof required.

Repo artifact model

Make the agent read the same durable context as the team.

Treat these files as the story's source material. The agent can summarize them, challenge gaps, update them with the implementation, and link them in the PR.

Scenario to proof

Carry scenario ids through implementation and review.

  • Scenario id: stable reference in ticket, scenario file, tests, and PR body.
  • Behavior: actor, preconditions, action, expected result, and side effects.
  • Proof layer: unit, integration, functional, manual, or UAT.
  • Trace: test name, PR evidence, and coverage-matrix entry reference the scenario.

Coverage matrix

Use the matrix to prevent scenario drift.

  • Update the coverage matrix when workflow behavior changes.
  • Mark which scenarios are covered by unit, integration, functional, or UAT evidence.
  • Record intentional gaps with a reason and owner.
  • Use the matrix as PR review input, not just a post-release document.

Build

Use a worktree as the implementation lane.

A worktree gives the agent an isolated checkout tied to the story. It keeps local state, branch state, dependency installation, and generated files separate from other work.

Worktree setup

Give each lane a reproducible local environment.

  • Load the repo Node version with nvm use before Node or pnpm commands.
  • Use pnpm install with the workspace lockfile and shared store assumptions.
  • Keep new worktree bootstrap fast: shared pnpm store, stable lockfile, documented local service setup.
  • Let post-checkout hooks install or verify worktree dependencies when configured.
  • Use Docker-backed dependencies for integration and functional test lanes.

Local gates

Run the narrowest proof that can fail.

  • pnpm fix for formatting and lint repair during implementation.
  • pnpm verify:pre-commit for staged snapshot safety.
  • pnpm verify:pre-push for push-safe repository checks.
  • pnpm verify:ci for local CI parity before high-risk handoff.
  • Run database migration lint/static checks whenever schema or data migrations change.
  • Document which checks can run in parallel and which need serialized ports, databases, or fixtures.

Test

Match the proof layer to the behavior being changed.

Unit, integration, functional, and UAT checks answer different questions. Coverage is useful, but it is only one signal inside a broader proof package. Make required thresholds CI-enforced, then publish the artifacts agents and reviewers need to inspect failures.

Unit

Logic in isolation

Use for validation, mapping, parsers, reducers, negative branches, and small services.

Fast and numerous
Integration

Pieces cooperating
